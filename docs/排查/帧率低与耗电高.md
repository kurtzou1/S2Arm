# 排查手册：帧率低 / 耗电高

适用范围：一局跑完以后帧率格或能耗格不过、没数据，或者想要 60 帧却只有 30、开了 60 帧游戏变快、换了游戏版本 60 帧没了。画面花屏看 [花屏与贴图错](花屏与贴图错.md)，两侧黑边看 [不满屏与宽屏异常](不满屏与宽屏异常.md)，没走直连看 [直连异常与退回通用](直连异常与退回通用.md)。

所有门槛、公式都抄自仓库里的判据代码，每条后面括号给出处（文件 + 函数或行号附近），读者可以自己去核；代码改了以代码为准。几个词先说清：

- **局目录**：跑一局留下的目录。真机执行器 `tools/dev_run.sh` 写在 `<作业目录>/out_<时刻>/`（`tools/dev_run.sh` 第 19、25 行），里面有 `host.log`（宿主日志）、`frames.tsv`（逐帧表）、`pw0.plist / pwh.plist / pw1.plist`（三次电池采样）等。手动起局见 [贡献者开发测试套件](../贡献者开发测试套件.md) 第 3.3、4.3 节。
- **MARK**：自动玩家到达可玩场景时在 `host.log` 打的 `S2A 标记 MARK：帧 <N>`（`tests/autoplay/autoplay.c` 第 1152 行）。帧率、能耗窗口都从它起算。
- 没到 MARK 怎么查见 [自动玩家没到 MARK](自动玩家没到MARK.md)。
- **目标帧率**：游戏自己要的帧率（30 或 60），不是我们希望的帧率。取法见 ② 的「目标帧率怎么取」。
- **直连 / 通用**：两种图形模式。直连 = 游戏的 NVN 图形调用直接译到 Metal；通用 = 经 Ryujinx 显卡模拟层。两种模式写的 `frames.tsv` 列不同。

结论先行：先确认这局的读数作数（不是局无效、到了 MARK、窗口满 55 秒、满屏），再看是哪一格不过。帧率不过先看目标帧率对不对，再看慢帧当帧哪一列高；想要 60 帧却只有 30，按 L1 交换间隔 → L2 引擎限帧 → L3 时间步逐层排；能耗不过先看同局帧率格是不是绿（帧率没保持，瓦数达标也不算过），再按 3 局中位、标充电 / 热状态比，最后按 `[能耗]` 行拆账对已知坑。快检 `tools/quality_check.py` 不查局无效，过了还要再跑 `tools/score_cells.py --diag=1`。

## ① 症状长什么样

截图对这类问题没用，下面用读数描述。

## ② 用哪个工具、看哪几行

命令都在仓库根目录跑。

### 自查一条命令：快检

```sh
python3 tools/quality_check.py <局目录> --report <报告目录>            # 一局出一份报告（report.md / report.json / attach.zip）
python3 tools/quality_check.py <局目录> [<局目录>…] [--out <表.tsv>]   # 多局各打一行
```

- 每个局目录打一行，列依次是：款 / 画面 / 帧率 / 满屏 / 直连默认启动 / 能耗 / 读数 / 截图 / 局目录（`COLS`）。「款」取局目录上一级目录名下划线前那段（`jobs()`），只影响画面复核找参考图，不影响帧率 / 能耗。
- 看图判官用你自己的模型：设 `OPENROUTER_API_KEY` 或 `ANTHROPIC_API_KEY`，或装好并登录 `claude` 命令行（`provider()` 按这个顺序挑）；三样都没有时才加 `--no-ai`，「画面」「直连默认启动」两列写「没数据」，帧率、满屏、能耗照判。判官失败时原因写在读数「AI 判官失败：…」里（`check()`）。
- 帧率列：`score_cells.cells()` 的帧率格，绿 → 过、红 → 不过、未测 → 没数据。和 `score_cells` 的一处不同：未满屏局也照判，读数注「未满屏局」（`check()`）。
- 能耗列：`window_power` ≤ `w_max(目标帧率)` 且帧率格绿 → 过；瓦数达标但帧率红 → 不过、读数注「帧率未保持」；没有功耗读数或帧率格未测 → 没数据。不看热档（`check()`；文件头第 19–20 行）。
- 不做局无效检查（见 ③ 1），过了以后再跑 `python3 tools/score_cells.py <局目录> --game=<款> --commit=<包提交> --diag=1`；`--diag=1` 只打印、不写记分板（`score_cells.py` 第 301 行）。

### frames.tsv 的列

每上屏一帧写一行，制表符分隔，首行列名；第 1 行（`frame` = 1、`wall_us` = 0）是起点，不进判据（`tests/真机契约.md` 第 3 节）。两种模式写的列不一样：

- 通用模式：表头写死在 `graphics/metal/cs/NxFrames.cs` 第 38 行 `Head`，共 32 列。
- 直连模式：`graphics/nvn/host_adapt.m` 第 553 行，只写 `frame wall_us disp_us gpu_us draw_n pass_n`，登记了 GC 采样钩子时再加 `alloc_b gc0 gc1 gc2 gc_pause_us`。直连层拿不到的列整列不出现（不写 0，免得被当成真读数）；屏上间隔被系统丢弃或没读数时 `disp_us` 留空；最后 8 次上屏不写（同文件第 508–515 行注释）。

| 列 | 单位 | 含义 | 哪种模式有 | 出处 |
|---|---|---|---|---|
| `frame` | — | 上屏序号，从 1 起 | 都有 | `tests/真机契约.md` §3 |
| `wall_us` | 微秒 | 与上一帧上屏的间隔（渲染线程 Present 时刻记时，带约 ±2 ms 抖动） | 都有 | `tests/真机契约.md` §3；`score_cells.py` 第 152 行注释 |
| `disp_us` | 微秒 | 画面真正上屏的间隔（有显示层才有值）。帧率格优先用它 | 都有（通用模式没有显示层时为 0） | `NxFrames.cs` 第 38 行注释；`score_cells.py` 第 153 行 |
| `gpu_us` | 微秒 | 这一帧的 GPU 时间 | 只有直连 | `host_adapt.m` `ft_row` |
| `draw_n` `pass_n` | 次 | 本帧绘制数、渲染遍数 | 都有 | `tests/真机契约.md` §3 |
| `upload_n` `rw_kb` | 次 / KB | 主目标外切遍上传数、附件读写量 | 只有通用 | 同上 |
| `rb_us` | 微秒 | 本帧 CPU 等 GPU 读回的阻塞 | 只有通用 | 同上 |
| `gpuq_us` | 微秒 | 本帧编码线程等命令分配器环（GPU 跟不上的反压） | 只有通用 | 同上 |
| `macro_us` | 微秒 | 本帧显卡宏执行总耗时（另有 `macro_n` / `macro_interp_n` / `macro_interp_us`） | 只有通用 | `NxFrames.cs` 第 38 行注释 |
| `xlate_n` | 次 | 本帧 Ryujinx 当场翻译的着色器程序数（着色器包没覆盖到的） | 只有通用 | 同上 |
| `pso_n` `pso_us` | 次 / 微秒 | 本帧现建管线（管线归档没命中）个数与耗时 | 只有通用 | 同上 |
| `shader_miss` | 次 | 本帧离线着色器库没命中、当场翻译的着色器数 | 只有通用 | `tests/真机契约.md` §3 |
| `alloc_b` `gc_pause_us` | 字节 / 微秒 | 本帧托管分配、本帧 GC 停顿 | 通用都有；直连要登记钩子 | 同上 |

### 目标帧率怎么取

`python3 tools/game_fps.py <局目录或 host.log>` 打印 `<帧率>\t<说明>`，取不到帧节拍行退出 1。`target()`（第 17–27 行）按顺序：

1. `host.log` 没有「帧节拍」行 → 按 60 判，并标「取不到」（调用方据此判局无效）。行的格式：`[gal] 帧节拍：交换间隔 <N>，每帧 <X> ms（<F> 帧/秒）`，生效的交换间隔每变一次打一行，**取最后一行**。通用模式由 `graphics/loop/RenderLoop.cs` 第 165 行打，直连模式由 `graphics/nvn/host_adapt.m` `ft_pace` 打（第 596 行）。
2. 包里带了 60 帧表且放开了出图间隔（`host.log`「帧率表 …：60 帧开；出图间隔放开」）→ 按 60（10-29 已修，见 ⑤）。
3. `host.log` 的程序号在 `tools/fps_truth.tsv` 里有行 → 以表里「目标帧率」为准。这张表是 Ryujinx 关垂直同步实测出来的（维护方真值脚本 + `tools/fps_truth.py`），用来分开「游戏声明间隔 1 但自己限到 30」和「我们慢到 30」（`game_fps.py` 第 5–6 行）。
4. 交换间隔 0（游戏关了垂直同步）→ 按 60。
5. 其余 → 帧节拍行里的帧/秒。

以打印的第二列（说明）为准，它写明按哪一步判的。

### 帧率格判据

`tools/score_cells.py` `cells()`（第 140–206 行）：

| 项 | 规则 | 行号 |
|---|---|---|
| 用哪一列 | 整张表里有任何一行 `disp_us` > 0 就用 `disp_us`，否则用 `wall_us`；该列为空的行跳过 | 第 153–154 行 |
| 窗口 | 帧号 > MARK 帧号的所有行，一直到表尾 | 第 155 行 |
| 窗口够不够 | 窗口里帧间隔之和 < 55000 ms → 帧率格「未测」（不判红），能耗也不判 | 第 160、171 行 |
| 帧预算 | 1000 ÷ 目标帧率（30 帧 33.3 ms，60 帧 16.7 ms） | 第 141 行 |
| 平均帧率 | 窗口帧数 × 1000 ÷ 窗口间隔之和（ms） | 第 162 行 |
| 慢帧 | 间隔 > 1.5 × 帧预算（30 帧 > 50 ms，60 帧 > 25 ms）的帧占窗口帧数的百分比 | 第 162 行 |
| 绿 | 目标帧率取到了，且平均 ≥ 目标 × 0.99，且慢帧 ≤ 1% | 第 163 行 |
| 未满屏 | 满屏判定为否时（直连出图层宽高比与屏比差 > 1%，或通用报过「出图未满屏」），帧率、能耗两格清成「未测」，读数照记、标「未满屏，读数不作数」 | 第 172–174 行；`fullscreen()` 第 121–132 行 |

`score_cells` 的读数里会写 `平均 x 帧/秒（要 N）`、中位、慢帧百分比、帧数。看板按同一个包最近 3 个有效局的「平均 / 要」中位数与慢帧中位数判（`vote()` 第 282–286 行），单局只是一票。

### 慢帧清单

列出 MARK 后的慢帧，和 `score_cells` 同一口径（同样的列选择、预算和窗口）：

```sh
python3 -c "
import csv, re, sys
sys.path.insert(0, 'tools'); from game_fps import of_dir
o = sys.argv[1]; fps = of_dir(o)[0]; lim = 1.5 * 1e6 / fps
mk = int(re.search(r'S2A 标记 MARK：帧 (\d+)', open(o + '/host.log', errors='replace').read()).group(1))
A = [r for r in csv.DictReader(open(o + '/frames.tsv', errors='replace'), delimiter='\t') if (r.get('frame') or '').isdigit()]
c = 'disp_us' if any(int(r.get('disp_us') or 0) > 0 for r in A if (r.get('disp_us') or '0').isdigit()) else 'wall_us'
W = [r for r in A if int(r['frame']) > mk and (r.get(c) or '').isdigit()]
K = [k for k in ('wall_us', 'disp_us', 'gpu_us', 'rb_us', 'gpuq_us', 'macro_us', 'xlate_n', 'pso_n', 'shader_miss', 'gc_pause_us', 'draw_n', 'pass_n') if k in A[0]]
S = [r for r in W if int(r[c]) > lim]
print(f'目标 {fps:g} 帧/秒，口径 {c}，慢帧（> {lim / 1000:.1f} ms）{len(S)} / {len(W)}')
print('frame', *K, sep='\t')
for r in S[:40]: print(r['frame'], *[r.get(k, '') for k in K], sep='\t')
" <局目录>
```

第一行的「慢帧 a / b」与 `score_cells` 帧率说明里的慢帧百分比、帧数对得上（a ÷ b）。逐帧怎么读见 ③ 4。

### 功耗：三次采样、公式、能耗格

执行器用 `idevicediagnostics -u <UDID> ioregentry AppleSmartBattery` 把电池的 IORegistry 存成 plist（`tools/dev_run.sh` 第 262 行；要装 libimobiledevice，没装就没有 plist）：

| 文件 | 时刻 | 出处 |
|---|---|---|
| `pw0.plist` | 起局前（推完文件、起 App 之前）的基线 | `dev_run.sh` 第 263 行 |
| `pwh.plist` | 执行器从 `host.log` 看到 MARK 的那一刻（窗口起点） | `dev_run.sh` 第 411 行 |
| `pw1.plist` | 收局：结束 App 之后、拉回文件之前；测试段剩不到 25 秒就不采 | `dev_run.sh` 第 451 行 |

判据只用 `pwh` → `pw1`；`pw0` 不进判据。公式（`score_cells.py` `window_power()` 第 100–108 行）：

```
瓦 = (pw1.AccumulatedSystemLoad − pwh.AccumulatedSystemLoad) ÷ (pw1.SystemLoadAccumulatorCount − pwh.SystemLoadAccumulatorCount) ÷ 1000
```

两个字段都在 plist 的 `IORegistry → PowerTelemetryData` 下。这是整机耗电，不管电来自电池还是充电器。不用 `AccumulatedSystemEnergyConsumed`：充电时它把充电功率也算进去（同函数注释给的对照：同一局系统负载口径 4.11 W，EnergyConsumed 折算 7.12 W）。单独算一局：

```sh
python3 -c "import sys; sys.path.insert(0, 'tools'); from score_cells import window_power; print(window_power(sys.argv[1]))" <局目录>
```

读不到打印 `None`。**Mac 局没有功耗**：`runtime/run_mac.sh` 不采电池 plist，`window_power` 返回 None，能耗格「未测」、快检「没数据」。

| 能耗格 | 规则 | 出处 |
|---|---|---|
| 门槛 | 目标帧率 ≥ 59（游戏要 60 帧）≤ 4.8 W；其余 ≤ 3.7 W | `score_cells.py` `w_max()` 第 208–211 行 |
| 帧率没保持 | 瓦数达标但同局帧率格不是绿 → 能耗也红，读数注「帧率未保持」（降频省电但掉了帧不算成果） | `cells()` 第 165–167 行 |
| 窗口无效 | 帧率窗口不完整（没到 MARK / 不足 55 秒）→ 能耗不判 | 第 171 行 |
| 未满屏 | 同帧率格，清成「未测」 | 第 173–174 行 |
| 充电 / 热档 | 只标状态、不挡判：读数括号里写「充电状态·热档位」，如「未充电·nominal」「充满·fair」 | `energy_state()` 第 215–234 行 |

`energy_state` 的取法：充电状态看 `pwh` / `pw1` 两端的 `FullyCharged` / `IsCharging`（任一端充满 → 充满；否则任一端充电 → 充电中；都 0 → 未充电；读不到 → 充电未知）。热档取窗口内 `host.log` 心跳行 `[心跳] 帧 N，热状态 K`（`ios/app.m` 第 266 行，每 10 秒一行）的最高值：0 nominal / 1 fair / 2 serious / 3 critical。看板对能耗取同一个包最近 3 个有效局的中位数判；全部中位超门槛时改按凉机（nominal）局重判，偏热局只能证明绿、不能单独证明红（`vote()` 第 246–274 行）。

## ③ 常见根因（现象 → 根因 → 怎么认出来 → 修在哪）

### 1. 这局读数根本不作数（局无效）
- 现象：快检给了结论，但 `score_cells` 各格写「—」、读数以【局无效】开头。
- 根因（`score_cells.py` `main()` 第 295–296 行，任一条成立）：
  - `infra()`（第 48–58 行）：机上资源包缺文件、设备通道挂死、收局拉回的 `host.log` 是空的、执行器 `RESULT=push|install|lock|suspect`。
  - `test_unready()`（第 60–82 行）：进局流程没匹配上；或自动玩家没打 MARK 但游戏一直在正常出图。
  - `fps_basis()`（第 84–98 行）：`host.log` 只有控制台流；带了帧率上限 `S2A_FPS`；`MARK 后静置`（`S2A_AP_SCENE=2` 诊断口径）；没有帧节拍行；手柄回放场景核对不符。
  - `scene_menu()`（第 34–46 行）：本局 MARK 后每帧绘制中位数不到同款其它局基线的 1/4，疑似停在菜单。
- 怎么认：`score_cells --diag=1` 的读数开头。
- 修在哪：不是游戏或宿主的问题，按原因重跑一局：正式口径用 `S2A_AP_SCENE=1`（MARK 后按固定动作序列跑，按玩家在玩的负载，`tests/真机契约.md` §1），不带 `S2A_FPS`；直连录像 `S2A_DIRECT_REC` 每帧等 GPU 写盘，功耗局不开（[贡献者开发测试套件](../贡献者开发测试套件.md) 3.2 节）。

### 2. 窗口不完整或未满屏（帧率 / 能耗「未测」）
- 现象：帧率说明里「窗口不足 55 秒」「没到 MARK」，或读数以【未满屏，读数不作数】开头。
- 根因：窗口不完整时画面停住、功耗自然低，记绿是假绿，所以不判（`score_cells.py` 第 158–159 行注释、第 171 行）；未满屏时帧率、能耗两格清成「未测」（第 172–174 行）。
- 怎么认：同上两处说明文字。
- 修在哪：窗口问题让局跑满（MARK 后 ≥ 55 秒）；满屏问题看 [不满屏与宽屏异常](不满屏与宽屏异常.md)。

### 3. 想要 60 帧却只有 30：卡在三层里的哪一层

三层的定义见 `docs/名单_60帧能力覆盖/_表头.tsv` 第 ② 条与 60 帧通用能力落地方案（维护方内部文档） 第 1 节：

| 层 | 是什么 | 缺了会怎样 |
|---|---|---|
| L1 交换间隔 | 游戏请求的上屏间隔（present interval）能否压到 1 | 游戏设间隔 2，就只有 30 帧 |
| L2 引擎限帧 | 引擎自己按更低帧率等待（虚幻 4 控制台变量、Unity `targetFrameRate`、自研常量），与 L1 无关 | L1 放开了，帧率还是 30 |
| L3 时间步 | 逻辑按帧推进的游戏，60 帧下必须按真实帧间隔重写步长 | 画面 60，游戏双倍速 |

三层的组合结论（落地方案 1.4 节）：缺 L3 时只有 L1 + L2 = 显示 60、逻辑 2 倍速，不能算 60 帧达标；缺 L2 时引擎自己限帧的款仍锁 30。判别步骤（用 ② 的「60 帧相关的行」）：

- **第 0 步：开关开着没有。** 依次找「能力清单：60 帧关」「帧率表 …：60 帧关」「【红】帧率表 … 整表不用」「帧率表：热状态严重 / 低电量模式开着」、有没有任何「帧率表」行。命中任一条就是开关 / 降档 / 版本问题，不是三层能力问题。
- **第 1 步：L1——游戏要的交换间隔是几。** 看最后一条帧节拍行；直连再看 present tick 行的 `游戏设 interval` 和 `interval mode`；帧率表行写「出图间隔放开」= L1 已放开。L1 的放开手段：帧率表 `present display` 行（`fps.c` 第 10 行）、游戏档 `graphics/nvn/games/<程序号>/game.tsv` 的 `present_interval display`、社区帧率补丁（如「Present interval 2 -> 1」类，见附录 B）。
- **第 2 步：L2——L1 放开了，帧率还是 30。** 只看上屏间隔分不出「游戏自己限到 30」和「我们慢到 30」（`game_fps.py` 第 6 行），要用真值表分：`tools/fps_truth.tsv` 里本款程序号目标帧率是 30 → Ryujinx 关垂直同步也只跑 30，是游戏自己限帧（`tools/fps_truth.py` 第 4 行：中位在 30 ± 2 判 30）。真值表没有本款时，按 `compat/truth/run_fps.sh <卡带目录> <输出目录> <墙钟秒>` 跑一局再 `python3 tools/fps_truth.py <款> <程序号> <输出目录>/stderr.txt` 生成。定位 L2 变量的现成工具（都只读）：虚幻 4 按变量名找地址 `tools/ue_cvar_loc.py <main.patched.bin> t.MaxFPS:f32:60 r.VSync:i32:0`，直接打印帧率表 `w` 行；Unity 判「只放开交换间隔够不够」`tools/unity_fps_judge.py <global-metadata.dat> <main.patched.bin>`；Unity setter 入口定位 `tools/il2cpp_fps_loc.py`（落地方案 2.2 节）。改法是帧率表 `w` 行：游戏数据区的值装载后每 100 ms 写一次（`fps.c` 第 11–14 行；每款 `w` 行上限 32 条，第 28 行）。
- **第 3 步：L3——画面到 60 了，游戏变快。** 跑附录 A 的逻辑速度判定。红 = 逻辑按帧推进、没补偿；补法是帧率表的 `speed <槽> <最小> <最大>`（每次出图按真实帧间隔 ÷ (1/30 秒) 写槽）+ 改写器 `c` 行让游戏速度函数改读这个槽（`fps.c` 第 15–19 行；完整实例 `runtime/fps/de0b6ac4efc1dda7.tsv`，落地方案 2.3 节）。

### 4. 慢帧：当帧哪一列高

用 ② 的慢帧清单逐帧看：

| 当帧哪列高 | 指向 | 依据 |
|---|---|---|
| `xlate_n` / `pso_n` / `shader_miss` > 0 | 着色器 / 管线首遇（包里没覆盖到、当场编） | `score_cells.py` 第 178–179 行把这类帧归「我方开销」 |
| `macro_us` ≥ 帧时 70% | 显卡宏执行太慢 | 同上 |
| `rb_us` 大 | CPU 等 GPU 读回 | `tests/真机契约.md` §5：窗口 `rb_us` 合计 > 墙钟 1% 或单帧 > 1 帧预算即红（`tools/frame_gate.py`） |
| `gpuq_us` 大 | GPU 跟不上，编码线程被反压 | `tests/真机契约.md` §3 |
| `gpu_us` 接近或超过帧预算 | GPU 时间本身超了（直连） | `host_adapt.m` `ft_row` |
| `gc_pause_us` > 帧预算 25% | GC 停顿（30 帧 8.3 ms / 60 帧 4.2 ms） | `tests/真机契约.md` §5 |
| 都不高 | 游戏自己读盘或等待；或上屏节拍问题（本节第 5 条） | `score_cells.py` 第 177 行「游戏加载停顿」 |

`score_cells` 另把全程 > 100 ms 的帧（`wall_us` 与 `gpu_us` 取大，第 176 行）按上表前两行归因成「我方 / 游戏加载停顿」，写在读数 `>100ms N（我方 a、游戏加载停顿 b）` 里。首遇类的一个已知根因：出包没给对目标 GPU 架构，管线归档整份不命中、首遇全部同步现编，单次现编 16.6–57.4 ms，补对架构后 0.2–0.6 ms；Mac 局要用 `S2A_PACK_PLAT=macos` 出的包（经验文档第 14 条；贡献者套件 3.1 节）。

### 5. 两套上屏节拍叠加
- 现象：帧率掉到几分之一，帧间隔散在多拍，CPU 很闲。
- 根因：一帧被锁了两次——上屏路径已按交换间隔跟显示链接的拍，GL 层另有一道按自己时钟的「交换锁垂直同步」，两套节拍相位对不上，每帧多错过 1–3 拍。
- 怎么认：数码宝贝 GL 直连标题页 12–16 帧/秒、整进程 CPU 0.08–0.12 核；修后上屏落在 1 拍占 99.3%。
- 修在哪：有显示链接时跟链接的拍（`nvn_be_link_wait_tick`），没有链接才用自己的时钟。出处：经验文档「两套上屏节拍叠加」条。

## ⑤ 踩过的坑

- **快检不查局无效**：`tools/quality_check.py` 只调 `cells()`，不跑 `infra` / `test_unready` / `fps_basis` / `scene_menu`（`check()` 第 160–163 行）。快检「过」之后必须再跑 `score_cells --diag=1` 看有没有【局无效】。
- **目标帧率的帧率表分支曾经不命中（10-29 已修）**：`game_fps.py` 原来的正则 `帧率表 (\S+)：出图间隔放开` 对不上宿主现行格式「帧率表 <路径>：60 帧开；出图间隔放开（每个显示节拍一帧）…」（`runtime/src/fps.c` 第 200 行）。修前带表款被按真值表判：例如真值表里登记 30 的款，开了 60 帧表也按 30 判。看旧局的判定时，以 `game_fps.py` 说明列写的依据为准。
- **贡献者套件文档有过时处**：[贡献者开发测试套件](../贡献者开发测试套件.md) 6.3 节能耗门槛只写 3.7 W，没有 60 帧款的 4.8 W（以 `score_cells.py` `w_max()` 为准）；首局格还写「冷局里扣掉同包热局同位置」，现行判法是任一到 MARK 的局按我方归因判（`score_cells.py` 第 182–186 行）；4.3 节说 `pw1` 在「收局前」采，代码里是结束 App 之后、拉回文件之前采（`tools/dev_run.sh` 第 451 行）。
- **判不出不算红，也不算绿**：逻辑速度判不出是证据不够，能力卡记 `unverified`；但发布包只在「绿」时缺省开 60 帧，判不出时发布包仍关（附录 A）。
- **瓦数达标不等于能耗过**：同局帧率格不是绿，能耗也红（`score_cells.py` 第 165–167 行）。
- **能耗单局不可信**：同包同配置三局之间能差 0.7 W；对比至少 3 局取中位，并标明热状态和是否在充电（经验文档第 3 条）。偏热局只能证明绿、不能单独证明红（`vote()`）。
- **A/B 一次只差一个变量**：做退化二分前，先在「好」的提交上用同一量法确认它真的干净（经验文档第 4 条）。同包 A/A ≥ 3 局（非充电优先）取极差作噪声底，B − A 的绝对值超过噪声底才算有差别；`tools/ab_noise.tsv` 里没有的款不判功耗，不借别款的数（`tests/真机契约.md` §5b；`score_cells.ab_power_noise()` 第 110–119 行）。
- **读回 / 同步类改动只信真机**：桌面测会严重低估（经验文档第 8 条）。Mac 离屏局没有显示链接，节拍叠加测不出（经验文档「两套上屏节拍叠加」条）。Mac 局没有功耗读数。
- **起局到 MARK 的墙钟不能判逻辑速度**：大头是读档加载，不随逻辑速度变。
- **抓现场会改变被测系统**：显式给 `S2A_SPIN_DUMP_S` 抓宿主栈时那一帧会卡 100 ms 以上，帧率局别开（`energy.c` 第 92–95 行）。
- **冷启动开关可能顺带清设备缓存**：读「热局命中」时别误判（经验文档第 12 条）。

## 附录 A：逻辑速度验证

### 现状：没有自动判定

判的是「固定一段墙钟里游戏逻辑走了多远」：按真实时间推进的游戏，帧率翻倍后每秒推进的逻辑时间不变（绿）；按帧推进、没补偿的游戏，每秒多推进一倍（红，高帧率下真快了）。

原来的自动判定 `fps_speed_judge.py` 读的是旧自动玩家摇杆探测时存的画面位移轨迹（`ap_trace.bin`）。11-01 自动玩家改成 AI 看屏驾驶后，摇杆探测和这份轨迹都没了，这个工具随之删除，**目前没有替代的自动判定**。`tools/ab_pair.sh <款> fps60` 照样跑关 / 开两局，跑完退出 2（判不出），不出结论，两局局目录留给人看。

### 现在怎么判（人判）

1. `bash tools/ab_pair.sh <款> fps60` 跑出关局（`S2A_FPS60=0`）和开局（`S2A_FPS60=1`），两局都要到 MARK，且开局 MARK 后实测帧率确实高（五问帧率格读数）。
2. 在两局里找同一种「有时钟意义」的东西比快慢：游戏内计时器 / 倒计时、昼夜或时钟显示、固定周期的动画（旗子、水面、待机动作）、过场字幕的切换间隔。拿同样墙钟长度的截图序列（局目录 `ap_mid.png`、`ap_end.png` 及 `vision/` 截图带的帧号）比。
3. 开局里这些东西快了接近帧率倍数 → 红；一样快 → 绿；看不出 → 判不出，不猜。
4. 红：登记 `docs/名单_60帧/<程序号>.tsv` 的逻辑速度 = 红（出包时自动成强信号，发布包关 60 帧）；补法是帧率表的动态步长，见正文第 3 步。

旁证（不是通用判据）：帧率表带动态步长的款，宿主每 1800 次出图打一行帧步汇总 `[nvn] frame step: game time <a> s in <b> s (<比> of real time)`（`graphics/nvn/gfx/nvn/hle_nvn.c`）。它数的是宿主写给游戏的步长，1.000 表示宿主按真实时间喂步长；不反映游戏自己按帧推进的部分，只能给这类款作参考。

### 一条命令跑关 / 开对照局：`tools/ab_pair.sh`

```sh
S2A_ROOTS=<出包输出>/roots bash tools/ab_pair.sh <款> fps60 [局目录]
```

同产物根、同存档、同进局路线（掌机档），先 `S2A_FPS60=0` 后 `S2A_FPS60=1` 各跑一局 Mac 局；两局任一没到 MARK 退出 3。fps60 目前跑完两局就退出 2（判不出），结论按上一节人判。满屏档位（`widen:<档位>`）仍由 `tools/widen_accept.py` 自动判，见 [不满屏与宽屏异常](不满屏与宽屏异常.md)。

### 记录结论的写法

要登记到 `docs/名单_60帧能力覆盖/<程序号>.tsv`（一款一个文件）时照 `docs/名单_60帧能力覆盖/_表头.tsv`：每层只用五档 `已具备 / 部分 / 缺 / 不需要 / 未知`，没有可复核依据就写「未知」、不猜；依据栏一律指到文件（+ 行号或可搜的原串）或某局 `host.log`；注释声称跑过、仓库里查不到原始记录的，写「读数仓库内无留存」，不当已验（表头第 ③ ④ 条）。按 R7 社区文字推断的，括注「据 R7，未实测」，与实测冲突以实测为准（表头第 ⑦ 条；[能力卡数据口径](../能力卡_数据口径.md) 3.1 节）。

### 换了版本：`tools/fps_relocate.py`

帧率表按主程序构建号前 16 位命名、表内 `build` 行与本包不符时整表不用（`fps.c` 第 9、159 行），换版本 60 帧就静默失效。

```sh
python3 tools/fps_relocate.py <旧版 exefs/main> <新版 exefs/main> runtime/fps/<旧构建号前 16 位>.tsv [--write]
```

- 判两版主程序数据段 / bss 是否同构：数据段起点、大小与 bss 大小都相同，且数据段里每一处不同都是「8 字节值差同一个常数」（代码段整体平移、指向它的指针跟着变）（`isomorphic()` 第 27–40 行）。
- 同构且表里没有 `c` 行 → 打出新构建号的表（`--write` 写 `runtime/fps/<新构建号前 16 位>.tsv`，已存在不覆盖）；不同构或有 `c` 行（代码地址要按指令重新定位）→ 报红退出 1、不出表（第 66–71 行）。退出码 0 出表 / 1 不能带用 / 2 参数或读文件错。
- 出的表只是候选，登记仍要关 / 开对照局判 ρ ≈ 1（文件头第 9 行）。
- 有 `c` 行或代码补丁要跨版本的，方法参考 Wonder 稳帧补丁跨版本定位（维护方内部文档）（掩码窗口唯一命中 + 原分支与邻接结构核对），仓库里没有自动化工具。
